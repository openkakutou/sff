# .sff v2 pixel encode: RLE8 and LZ5 implemented as semantic-round-trip encoders (LZ5 literal-only, no back-references); RLE5 encode stays deferred with the same rationale as its decode side

**Context:** Backlog item 002 adds the encode side for `.sff` v2's `V2FormatRLE8` and `V2FormatLZ5` pixel formats — `DecodeV2Sprite` already decodes both (this repo's migrated `character/sff` code), but `EncodeV2Sprite` returned "unsupported format" for every compressed format, per this repo's own `.vibe/decisions/007-sff-v2-serialize-shape-and-scope.md` (migrated from `character`, not yet copied into this repo — see the note below). `character`'s own history never implemented RLE8/LZ5 encode either (its `.vibe/index.md` records "RLE8/LZ5/RLE5 encode and RLE5 decode still pending" as of this repo's extraction), so this is genuinely new work, not a migration of existing encoder code.

**Decision:**
- `EncodeV2Sprite(V2FormatRLE8, img)` encodes indexed pixel data into a valid RLE8 stream (4-byte declared-length prefix + run-length-encoded control stream), the format `decodeV2RLE8` already understands. It targets a **semantic** round trip through `DecodeV2Sprite` (decode → encode → decode is pixel-identical), not a byte-exact reproduction of how any particular real encoder would have compressed the same pixels — consistent with `.vibe/decisions/007-...md`'s established "`.sff` is binary, byte-exact preservation is not a goal" reasoning for this package's other write paths. A run of identical bytes is written as a run marker (count capped at the format's 6-bit field, splitting longer runs across multiple markers); a run of length 1 is written as a plain literal byte unless that byte's own bit pattern would be misread as a run marker on decode (top two bits `0b01`), in which case it is still marker-encoded with count 1.
- `EncodeV2Sprite(V2FormatLZ5, img)` encodes indexed pixel data into a valid LZ5 stream the same way, but **always emits literal runs, never back-reference copies** — the simplest correct encoder for this format, at the cost of not compressing as well as a real encoder that exploits repeated patterns via back-references. Real LZ5 sprites are 5-bit indexed (`ColorDepth` 5): pixel values above 31 cannot be represented by this format's literal encoding and return a descriptive error instead of being silently truncated or misencoded.
- `V2FormatRLE5` stays unimplemented on the encode side, exactly as it already is on the decode side. The rationale is the same one already recorded in `character`'s backlog (item 030, never migrated into this repo as an ADR): a scan of a real, local corpus of ~562 `.sff` v2 files found RLE8/LZ5/PNG8/24/32 all used thousands of times each, and RLE5 (format code 3) used **zero** times — the reference decoder project this package's algorithms are ported from (`sff-extractor`) has no RLE5 support either. Shipping an encoder (or decoder) for a format with no known real-world fixture would be exercised only by hand-built synthetic data, violating this package's own "real-file compatibility over spec purity" constraint (CLAUDE.md).

**Reason:** A correctness-first, semantically-round-tripping encoder is more valuable than a byte-exact or maximally-compressed one for this package's actual consumers (`character-editor`'s sprite-saving feature only needs the resulting file to decode back to the same pixels), and matches the precedent `.vibe/decisions/007-...md` set for the PNG formats' own encode side. Skipping back-references for LZ5 keeps the encoder's correctness easy to verify by construction (every operation it emits is a small, directly-checkable literal run) rather than introducing a second, harder-to-verify code path (finding and encoding valid back-references) for a compression-ratio benefit no acceptance criterion asks for. Deferring RLE5 keeps this item's scope — and this package's real-file validation constraint — intact, and avoids spending effort on a format with no known real caller.

**Rejected alternatives:**
- Implementing LZ5 back-reference encoding (an actual LZ77-style compressor) for a smaller output — rejected: no acceptance criterion requires compression ratio, only pixel-identical round trips and real-fixture validation; a back-reference encoder is meaningfully harder to get right (must never point at data it hasn't decoded-equivalent-written yet, must respect the format's own distance/length encoding limits) for no required benefit.
- Implementing RLE5 encode now since a real decoder algorithm (`Rle5Decode`) is known and portable — rejected for the same reason `character`'s item 030 gives: no real fixture exists to validate against, and an unverified encoder is worse than an honest "unsupported format" error.
- Copying `character`'s decision files 006/007/015 into this repo verbatim as part of this item — out of scope: this item's job is the encode-side code and the RLE5 rationale it explicitly depends on (the acceptance criteria only ask for that), not a general documentation backfill of every pre-existing reference gap left by item 001's migration.

**Superseded (RLE5 portion only):** decision `014` implements `V2FormatRLE5` encode (and decode) anyway, at the Product Owner's explicit request, without waiting for the real fixture this decision treats as a prerequisite. The RLE8/LZ5 reasoning above is unaffected.
