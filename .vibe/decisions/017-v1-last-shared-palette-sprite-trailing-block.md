# A v1 file's last real sprite can overstate its own declared Length by 768 bytes when SharedPalette is true

**Context:** Backlog item 007's real-file corpus scan found 17 sprites across 7 real character files (e.g. Marvel's `Thor`, the bundled `Kung Fu Man`'s own `ending.sff`/`intro.sff`) failing with "reading pixel data: EOF". Investigation (comparing each failing sprite's declared `[Offset, Offset+Length)` span against the real file's actual size and neighboring subheader positions) found a single, consistent shape: in every case, the failing sprite is the *last sprite in the file that owns real pixel data* (`Length > 0`, no earlier/later real-data sprite past it), `SharedPalette` is `true`, and the declared span ends exactly 768 bytes past the file's actual end (for `Thor`, past where the file's own trailing zero-length/linked sprite subheaders occupy the remaining bytes instead). This is the same 768-byte size as `V1PaletteBlockSize`, which a `SharedPalette: false` sprite's `Length` already legitimately includes and this package already subtracts (see decision `012`).

**Decision:** `resolveV1Pixels` now retries a failed pixel-data read once, subtracting `V1PaletteBlockSize` from the attempted length, when — and only when — the sprite has `SharedPalette: true` and the read failed with `io.EOF`/`io.ErrUnexpectedEOF` (a short read, not some other I/O failure). If the shorter read also fails, the original error is still returned. Confirmed against a real, trimmed fixture (`testdata/files/v1-last-sprite-shared-palette-trailing-block.sff`, sourced from a real `Goku SSJG` file) and against the full corpus: this resolved all 17 previously-failing sprites, 0 regressions across the other 665,267 successfully-decoding sprites.

**Reason:** The retry is narrowly scoped to the exact failure mode observed (a short read on a `SharedPalette` sprite) rather than a general "always try shorter" fallback, so it cannot mask an unrelated read failure (a genuinely corrupt/truncated file still errors normally — see `TestResolveV1Pixels_NonSharedSpriteEOF_StillReturnsError`, which confirms a `SharedPalette: false` sprite's own EOF is never silently retried this way). The likely real-world cause — some authoring tool reserving palette-block-sized space for a file's last sprite regardless of the shared-palette flag — doesn't need to be proven for the fix to be safe: a shorter, still-length-consistent read either produces a valid decode (this package's own PCX decoder validates its input structurally) or fails again with the original error surfaced.

**Rejected alternatives:**
- **Always subtracting `V1PaletteBlockSize` for a `SharedPalette: true` sprite** (matching the `false` case unconditionally): rejected — would silently truncate the pixel data of the enormous majority of `SharedPalette: true` sprites that decode correctly today with their full declared length, a real regression for one narrow real-file shape's sake.
- **Detecting "last sprite in file" structurally and only special-casing that position**: rejected as unnecessarily complex — the retry-on-EOF approach already only ever fires for a sprite whose read would otherwise fail, which is exactly (and only) this shape in the entire corpus; no separate position-tracking logic is needed to scope it correctly.
