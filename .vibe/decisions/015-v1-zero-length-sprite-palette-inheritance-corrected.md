# v1 palette inheritance: two gaps closed by real-file corpus testing

**Context:** Backlog item 005's real-file corpus scan (562 real character `.sff` files) found `ResolveV1Palette` failing on two distinct, real shapes decision `011`'s documented rule didn't account for — both errors of the same form ("declared length N is smaller than the 768-byte palette block it must contain"), but with different root causes:

1. **Zero-length sprites** (2,949 sprites, e.g. `Arcana Heart/Saki Tsuzura`, `Capcom/Commando (CVS)`): decision `011`'s rule only consulted `SharedPalette` — `false` meant "must own an embedded block". Real files carry zero-length "copy" sprites (`Length == 0`, already known from `011`'s own pixel-linking rule to have no pixel data of their own) not marked `SharedPalette`, which the old rule wrongly demanded own a palette block they structurally cannot have. Verified against Ikemen-GO's own source (`src/image.go`): when a sprite's declared size is `0`, the engine always `shareCopy`s the previous resolved sprite entirely (pixels and palette alike), regardless of any palette-sharing flag.
2. **A `SharedPalette`-true sprite 0 with no real embedded data** (1,184 sprites across 21 files, e.g. `Capcom/Kobun/servbot.sff`): a file's very first sprite has nowhere to inherit from, yet decision `011` said index 0 "always decodes its own block regardless of its own SharedPalette bit". Real files exist where sprite 0 is marked shared and its declared length is far too short for a block (partial PCX pixel data only, no trailing palette). Verified against Ikemen-GO's own source: `SharedPalette` ("samepal") true means "use an already-resolved palette, not decode my own"; with no earlier sprite, the engine allocates a fresh, empty palette bank (`pl.NewPal()`) rather than attempting to read anything.

**Decision:**
- `resolveV1Palette` checks `Length == 0` first: when true (and the sprite isn't table index 0), it recurses to the immediately preceding sprite's resolved palette — the same predecessor `resolveV1Pixels` already resolves pixel data from — before considering `SharedPalette` at all.
- In the "must own an embedded block" fallback, a declared length shorter than the 768-byte block now returns an empty (zero-value) `Palette` instead of an error **only when `SharedPalette` is true** — the sprite never claimed to own real data in the first place. A non-shared sprite with too-short a length still errors: it explicitly claims ownership, so an implausible length there is a genuine defect, not a documented shape (unchanged, still covered by an existing test with `SharedPalette: false`).
- Decision `011`'s group/image-zero special case, and its existing "sprite 0 decodes its own sufficiently-long block even when marked shared" behavior, are both unchanged — this only adds a fallback for when there is not enough data to decode at all.

**Reason:** Matches the real reference decoder's verified behavior for both shapes, and closes exactly the class of bug decision `011` itself flagged as fixture-driven testing's job to catch — plausible-looking rules that were subtly incomplete rather than obviously wrong, only exposed at real-file scale (0 occurrences of either shape in this repo's existing trimmed/synthetic fixtures; 4,133 sprites combined across 562 real files).

**Rejected alternatives:**
- *Return an empty `Palette` for any too-short length, regardless of `SharedPalette`* — rejected: would silently paper over a genuinely malformed non-shared sprite (e.g. `Length: 20`, an existing, intentional error-path test) — the `SharedPalette` bit is what distinguishes "never claimed to own data" from "claims ownership but the file is broken".
- *Also change the existing sufficiently-long, `SharedPalette`-true sprite-0 case to always return empty, matching Ikemen-GO's `samepal` treatment even when a real block happens to be present* — rejected: contradicts an existing, already-verified passing test (`TestResolveV1Palette_SpriteZero_DecodesItsOwnBlockEvenWhenMarkedShared`) grounded in a different, sff-extractor-sourced reference behavior; changing that specific case isn't forced by any real corpus evidence found here (no real file in this scan combined `SharedPalette` true, index 0, and a sufficiently long, decodable length), so it's left untouched rather than guessed at.
- *Mark decision `011` as superseded* — rejected: `011`'s pixel-linking rule, its group/image-zero palette special case, and its "sprite 0 decodes a sufficiently long block" case are all still accurate and unchanged; only the two missing too-short-length shapes needed correcting, which this decision documents as an addition, not a replacement.
